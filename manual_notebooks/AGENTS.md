# Архитектура моделей и бэкендов

Эти инструкции действуют для `manual_notebooks/` и всех вложенных каталогов.
Описание пользовательского сценария и примеры находятся в [README.md](README.md).

## Назначение и границы

Ноутбуки задают параметры эксперимента и показывают результаты. Повторно
используемая логика скачивания, обучения и предсказания находится в `scripts/`.
Архитектура состоит из реестра моделей, адаптеров провайдеров и небольшой фабрики.
Не переносите вызовы SDK провайдеров в общий код выбора моделей или в ноутбуки.

Сейчас реализованы `ultralytics` и `rfdetr`. Для будущих интеграций предусмотрен
`mmdetection`. Другие бэкенды не входят в согласованный план:
соответствующие модели сохраняются в каталоге отключёнными, с поясняющими
комментариями. Не добавляйте зависимости и фиктивные реализации будущих бэкендов.

## Карта модулей

| Модуль | Ответственность |
| --- | --- |
| `scripts/common.py` | Общие пути, словарь выбора `MODELS`, публичный доступ к реестру |
| `scripts/registry.py` | `MODELS_REGESTRY`, метаданные реализаций, проверка согласованности ключей |
| `scripts/contracts.py` | Структуры данных и протоколы `Backend` и `Predictor` |
| `scripts/backends/__init__.py` | Фабрика `get_backend(spec)` |
| `scripts/backends/ultralytics.py` | Скачивание, обучение, загрузка, подсказки и нормализация результатов Ultralytics |
| `scripts/backends/rfdetr.py` | Адаптер RF-DETR: проверка версии SDK, скачивание, обучение, загрузка и нормализация предсказаний |
| `scripts/rfdetr_dataset.py` | Подготовка каталогов YOLO для RF-DETR с сохранением исходных разбиений и хешей файлов |
| `scripts/visualization.py` | Отображение нормализованных рамок, классов и масок независимо от SDK |
| `scripts/workflows.py` | Выбор включённых моделей, последовательное обучение, отчёт о пропусках и загрузка выбранных артефактов |
| `scripts/weight.py` | Проверка наличия весов, пакетное скачивание, таблицы для ноутбуков |
| `tests/test_models.py` | Автономные тесты с имитациями провайдера и временными файлами |
| `tests/test_rfdetr.py` | Автономные тесты RF-DETR, подготовки датасета, артефактов и предсказаний |
| `requirements-rfdetr.txt` | Отдельная закреплённая зависимость RF-DETR с компонентами обучения |

## Выбор моделей и реестр

- `common.MODELS` — единственный словарь включения и отключения моделей. Не заменяйте его списком `SELECTED_MODELS` и не вводите параллельный источник выбора.
- `MODELS_REGESTRY` использует те же ключи. Это согласованное имя публичного API; не исправляйте его написание попутно с другими изменениями.
- `ModelSpec` описывает конкретную реализацию: идентификатор, бэкенд, задачу, конструктор, файл весов, операции и причину недоступности.
- Бэкенд обозначает программную реализацию, а не автора или семейство архитектур. Не считайте все YOLO совместимыми с Ultralytics.
- Семейства без конкретного файла весов остаются неготовыми к запуску. Не выбирайте размер модели автоматически.
- Имя файла весов задаётся явно: например, `yolov12n` соответствует `yolo12n.pt`. Не восстанавливайте его простым добавлением `.pt` к идентификатору.
- При добавлении модели обновляйте и `MODELS`, и реестр. Сохраняйте проверку совпадения ключей, идентификаторов и булевых флагов.
- Импорт каталога и проверка наличия файлов не должны загружать Ultralytics, PyTorch или другие SDK провайдеров.

## Контракты и поток выполнения

Общий поток: `MODELS` → `ModelSpec` → `get_backend(spec)` → операция адаптера.

Адаптер реализует протокол `Backend`:

```python
download(spec) -> ModelArtifacts
train(spec, initial, dataset, config) -> TrainingRun
load(spec, artifacts, device) -> Predictor
```

Объект `Predictor` предоставляет `predict(image, *, prompts=None, **options)`
и возвращает список `Prediction`. Загруженная модель переиспользуется между
вызовами; не загружайте веса заново для каждого изображения.

- Используйте `ModelArtifacts` для путей к весам и необязательной конфигурации. Не возвращайте наружу только внутренний объект SDK.
- Общие параметры обучения находятся в полях `TrainConfig`. Метод `options_for(backend)` объединяет `options` и `backend_options[backend]`, причём настройки выбранного бэкенда имеют приоритет. Параметры другого провайдера не передаются в SDK. Например, `workers`/`plots` относятся к Ultralytics, `num_workers` — к RF-DETR. Не приписывайте одинаковую семантику настройкам разных библиотек и не разрешайте переопределять общие поля через options.
- Проверяйте совместимость задачи модели и весов до запуска обучения. Текущий `DatasetSpec` описывает локальный YAML YOLO с задачей `detect` или `segment`. Ultralytics проверяет датасет при обучении; RF-DETR дополнительно проверяет разметку при подготовке каталогов.
- Адаптер переводит вызовы и результаты между общим интерфейсом и SDK. Отображение таблиц pandas/IPython остаётся в слое для ноутбуков.
- Нормализованные результаты содержат массивы NumPy на CPU. Рамки `xyxy` и булевы маски используют координаты исходного изображения; `native` сохраняет исходный результат провайдера.
- Не назначайте семантические классы маскам, полученным без классификации: для них `class_ids` и `names` равны `None`.
- Текущий API обрабатывает отдельные изображения: локальный путь, PIL или массив H×W×3 `uint8` в BGR. Сопровождение объектов на видео с сохранением состояния в этот интерфейс не входит.
- Подсказки зависят от модели. SAM3 использует отдельные интерфейсы для интерактивных точек/рамок и поиска по тексту/примерам объектов. Не направляйте все варианты в один универсальный вызов.

## Доступность, ошибки и артефакты

- Наличие предсказания не означает наличие обучения. В текущем адаптере SAM, MobileSAM, SAM2, SAM3 и FastSAM поддерживают только скачивание и предсказание.
- Пакетное скачивание проверяет все включённые записи до начала загрузок. Существующие файлы переиспользуются; новые скачиваются во временный каталог, чтобы прерванная загрузка не считалась готовыми весами.
- `train_models` сообщает о неподдерживаемых моделях и пропускает их. Для обнаруженной до обучения недоступности используйте `UnsupportedOperation`.
- Некорректные данные и непредвиденные ошибки обучения останавливают выполнение. Не превращайте произвольные исключения в молчаливые пропуски.
- Каждый запуск получает отдельный каталог в `RUNS_DIR`, лучшие и последние веса и `manifest.json`. Сохраняйте идентичность модели, хеш исходных весов, версию провайдера, заданные и фактические параметры, описание датасета и метрики.
- `weights/trained/<model-id>.pt` — удобная копия последних успешных весов. Для воспроизводимого предсказания используйте артефакт конкретного запуска.
- `load_model` принимает явно выбранные артефакты. Не подменяйте отсутствующие обученные веса предобученными.
- Сохраняйте совместимость `weight.inspect_weights()` и `weight.download_weights(return_paths=...)`. При `return_paths=True` возвращается словарь идентификаторов и путей; иначе — `None`.

## Реализация RF-DETR

- RF-DETR — отдельный провайдер `rfdetr`, не RT-DETR. Запись `rt-detr` продолжает использовать конструктор `RTDETR` бэкенда Ultralytics.
- Адаптер рассчитан строго на `rfdetr[train]==1.12.1`; другая версия вызывает понятную ошибку. Зависимость находится в `requirements-rfdetr.txt`, SDK импортируется только при выполнении операций. При обновлении версии перепроверьте API и имена артефактов, затем обновите ограничение и тесты вместе.
- Для детекции реализованы `rf-detr-n`, `rf-detr-s`, `rf-detr-m`, `rf-detr-l`; для сегментации — `rf-detr-seg-n`, `rf-detr-seg-s`, `rf-detr-seg-m`, `rf-detr-seg-l`. Все поддерживают download/train/predict и по умолчанию выключены. Семейства `rf-detr` и `rf-detr-seg` требуют явных конструктора и файла весов.
- Имена исходных весов берутся из реестра: детекторы используют `rf-detr-{nano,small,medium}.pth` и `rf-detr-large-2026.pth`, сегментаторы — `rf-detr-seg-{nano,small,medium,large}.pt`. Не выводите имя файла из локального идентификатора.
- Скачивание использует `rfdetr.assets.model_weights.download_pretrain_weights` во временном каталоге; завершённый непустой файл перемещается в каталог исходных весов. Повторное скачивание переиспользует существующий непустой файл без импорта SDK.
- Общие поля обучения переводятся в `epochs`, `batch_size`, `resolution`, `device`, `seed`. Неизвестные и зарезервированные RF-DETR options отклоняются. Разрешение детекторов кратно 32, Seg Nano — 12, остальных сегментаторов — 24. Не округляйте размер автоматически; 384 подходит всем восьми вариантам.
- Для загрузки используется `RFDETR.from_checkpoint`: архитектура, классы и разрешение восстанавливаются из выбранных весов. Адаптер проверяет конкретный класс модели и наличие головы сегментации. Отсутствующие или несовместимые веса не заменяются исходными.
- Каждый запуск сохраняет `checkpoint_best_total.pth`, `last.ckpt` и `manifest.json`. Фактическая конфигурация читается из `training_config.json`, последние непустые значения метрик — из `metrics.csv`. Манифест содержит статус, описание модели и датасета, версию SDK, запрошенные и фактические параметры и хеш исходных весов; ошибки записываются со статусом `failed`.
- Копия лучших весов в `weights/trained/<model-id>.pt` обновляется через временный файл после успешного обучения. Расширение `.pt` сохраняет общий интерфейс и не преобразует формат RF-DETR. Продолжает действовать общий пропуск моделей, у которых этот файл уже существует.
- Predictor загружает модель при первом вызове и переиспользует её. BGR-массив преобразуется в RGB для SDK. Поддерживаются `conf` либо `threshold`, `imgsz` и `antialias`; `imgsz` должен совпадать с разрешением загруженной модели. Подсказки и неизвестные параметры отклоняются. Маски проверяются на соответствие исходным размерам изображения.
- В ноутбуке используйте `plot_prediction(image, prediction)` из `scripts.visualization`, а не Ultralytics-специфичный `prediction.native.plot()`. Исходный результат SDK по-прежнему доступен в `native`.

### Подготовка датасета для RF-DETR

`stage_dataset` вызывается адаптером перед обучением и создаёт `<run>/dataset/`
с `data.yaml` и каталогами `train/images`, `train/labels`, `valid/images`,
`valid/labels`; при наличии test добавляется соответствующая пара каталогов.
Причина подготовки — штатный загрузчик RF-DETR 1.12.1 ожидает пути к каталогам,
а текущий датасет задаёт выборки через `train.txt`, `val.txt`, `test.txt`.
RF-DETR также понимает другие структуры, например `images/train`: именно
файлы списков требуют адаптации, а не единственно допустимое имя каталога.

- Входом остаётся `DatasetSpec`: локальный YAML, задача detect или segment. Поддерживаются каталоги, файлы списков и списки путей в YAML. Относительный `path` разрешается от каталога YAML; строки `./...` в файле выборки — от каталога этого файла, остальные относительные строки — от cwd, как в текущем соглашении Ultralytics.
- Состав и порядок исходных выборок сохраняются; новое случайное разбиение не создаётся. Train и val обязательны, test необязателен. Имена классов сохраняются, идентификаторы должны идти подряд от нуля.
- Изображения и существующие YOLO labels связываются символическими ссылками. Уникальные числовые имена внутри выборки исключают коллизии одинаковых исходных имён. Разметка ищется заменой последнего компонента `images` на `labels`. Исходные файлы не изменяются; отсутствие label означает негативное изображение и представляется пустым файлом в подготовленном каталоге.
- Для детекции проверяются нормализованные рамки, для сегментации — полигоны минимум из трёх точек. Проверяются конечность координат, диапазон и класс. Не превращайте рамки в фиктивные маски.
- В манифест записываются пути и SHA-256 исходного YAML, файлов выборок, изображений и существующих labels. Символические ссылки не являются автономным снимком датасета: исходные файлы должны оставаться доступными и неизменными для повторного использования подготовленного каталога.

## Как добавлять будущий бэкенд

При явной задаче на интеграцию нового провайдера:

1. Добавьте модуль адаптера в `scripts/backends/`, реализующий существующие контракты, и подключите его в фабрике. Импорт SDK должен оставаться отложенным.
2. Обновите `ModelSpec.unavailable_reason`: сейчас он допускает `ultralytics` и `rfdetr`. Одного изменения фабрики недостаточно.
3. Укажите реальные варианты, файлы весов, конфигурации и поддерживаемые операции в реестре. Уберите отметку о недоступности только у реализованных записей.
4. Проверьте текущие предположения общего кода: `DatasetSpec` и адаптер Ultralytics ориентированы на YAML YOLO, а `weight.py` использует текущую схему локальных путей. Адаптируйте эти границы, если новому провайдеру нужен другой формат или несколько артефактов.
5. При преобразовании датасета сохраняйте состав train/val/test и соответствие классов. Не создавайте новые случайные разбиения внутри адаптера.
6. Нормализуйте результаты в `Prediction` и добавьте тесты нового маршрута через фабрику, обработки ошибок, артефактов и выходных координат.

Не создавайте отдельный класс для каждого размера модели, если различия можно
выразить метаданными одного адаптера.

Для будущей интеграции MMDetection предпочтителен экспорт аннотаций в COCO JSON
по исходным train/val/test. `CocoDataset` позволяет оставить общий каталог
`images/` и задать отдельные `ann_file` для выборок и общий `data_prefix.img`;
переносить изображения или повторять структуру RF-DETR не требуется. YOLO labels
и текстовые списки не являются входом стандартного `CocoDataset`: потребуется
конвертация аннотаций или отдельный загрузчик. Это направление будущей интеграции,
а не уже реализованная возможность. См. [руководство MMDetection](https://github.com/open-mmlab/mmdetection/blob/main/docs/en/advanced_guides/customize_dataset.md).

## Проверка изменений

Из корня репозитория:

```bash
.venv-notebooks/bin/python -m unittest discover -s manual_notebooks/tests -v
```

Для изменений логики проверяйте затронутые сценарии: реестр, маршрутизацию,
переиспользование и сбои скачивания, пропуски обучения, артефакты запусков,
совместимость разметки, подсказки и координаты результатов.
При изменении ноутбука проверяйте JSON и синтаксис ячеек с учётом IPython-магии.
Не перезаписывайте существующие пользовательские изменения и исторические результаты.

Автономные тесты не требуют GPU, скачивания весов или полного обучения.
Проверку с реальным SDK проводите на доступных локальных весах и явно отделяйте
её результат от тестов с имитациями. Не запускайте длительное обучение только
ради проверки обычного изменения адаптера.

При добавлении RF-DETR прошли 36 автономных тестов, проверка JSON и синтаксиса
ячеек ноутбука; соответствие восьми вариантов, имён весов и ограничений разрешения
проверено по исходникам wheel RF-DETR 1.12.1. Полный импорт SDK в локальном
окружении не прошёл из-за отсутствующих зависимостей (`deprecate`, при отдельной
проверке конфигурации — `pydantic`). Реальное предсказание и обучение RF-DETR
не запускались. Не представляйте эти проверки исходников и имитаций как проверку
обучения или предсказания реального SDK.

## Язык

Описания в Markdown, README, комментарии и docstrings пишите на русском.
Сообщения выполнения, ошибки, статусы, заголовки таблиц и подписи графиков —
на английском. Поле `ModelSpec.note` также выводится пользователю и должно быть
на английском. Имена API, ключи данных и входные текстовые подсказки моделей
не переводите ради языка документации.
