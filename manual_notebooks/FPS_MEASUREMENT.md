# Измерение FPS, задержки и памяти

`fps_measure.ipynb` сравнивает включённые в `scripts.common.MODELS` модели через
существующие адаптеры Ultralytics и RF-DETR. За основу взяты прогрев,
синхронизация и поток с заменой непрочитанных кадров из `first.ipynb`.
Исторические результаты не переносятся в новые измерения. Команды STOP/MOVE
исключены: измеряется получение предсказания, а не управление роботом.

## Подготовка и запуск

1. Выберите Jupyter kernel с PyTorch и зависимостями нужных провайдеров.
   Дополнительные зависимости: `python -m pip install -r manual_notebooks/requirements-benchmark.txt`
   из корня проекта. RF-DETR требует отдельного `requirements-rfdetr.txt`.
2. Откройте ноутбук из корня проекта или `manual_notebooks/`. Измените флаги
   `cmn.MODELS`, явные пути `CHECKPOINTS`, `IMAGE_PATHS` и `DEVICES`.
   Отсутствующие обученные веса не заменяются исходными; скачивания и обучения нет.
   Для воспроизводимости лучше указать лучшие веса конкретного training run,
   а не изменяемую копию `weights/trained/<id>.pt`.
3. Настройте `PREDICTION_OPTIONS` отдельно для каждой модели. Для Ultralytics
   явно заданы `imgsz=640`, `conf=0.25`, `rect=True`;
   RF-DETR использует разрешение выбранного checkpoint и `conf=0.25`.
   Размеры входных изображений сохраняются в manifest; `imgsz` не всегда равен
   фактической форме входного тензора. RF-DETR отклонит несовместимый `imgsz`.
   Точность вычислений остаётся штатной для установленного SDK; для экспериментов
   с FP16/квантизацией укажите поддерживаемую вашей версией настройку отдельно.
   Устаревший `half` в новых Ultralytics вызывает предупреждения при каждом вызове,
   поэтому в общих настройках он не задан. При необходимости задайте `PROMPTS`
   в JSON-совместимом виде.
4. После конфигурации выполните ячейку прямого измерения и/или отдельную ячейку
   синтетического потока. Флагов включения нет: запуск определяется выполнением
   ячейки. Run All выполняет оба режима. Текущие настройки notebook: CPU,
   30 кадров прогрева, 30 секунд, 1 повтор; число повторов задаёт `REPETITIONS`.
   Поток: 10, 20, 30, 60 и 300 FPS; порядок скоростей перемешивается отдельно
   в каждом повторе с сохранённым seed. Один набор direct + stream занимает
   минимум 3 минуты на пару модель/устройство при одном повторе
   (9 минут при трёх), без учёта загрузки и прогрева.
5. Для короткой проверки задайте 2 кадра прогрева, 1 секунду, 1 повтор и одну
   скорость. Такой запуск проверяет работоспособность, но не даёт устойчивой оценки.

Каждая пара модель/устройство работает последовательно в новом процессе того же
Python, что и kernel. Это отделяет память моделей друг от друга и от ноутбука.
Сам ноутбук и чужие GPU-процессы всё ещё могут конкурировать за ресурсы: перед
сравнением освободите устройство. Загрузка модели ленивая, поэтому прогрев обязателен.
Модель переиспользуется между повторами; CUDA cache между ними не очищается.
Измеряется существующий путь адаптера. Например, RF-DETR может сообщать, что модель
не оптимизирована для inference: этот notebook не включает дополнительную
компиляцию/оптимизацию и не представляет полученный FPS как предельную скорость SDK.

## Что измеряется

| Режим | Начало и конец | Интерпретация |
| --- | --- | --- |
| Direct | Вызов `Predictor.predict` → завершение и синхронизация | Последовательное batch=1 предсказание через адаптер |
| Stream prediction | Тот же вызов для полученного кадра | Задержка обработки без ожидания очереди |
| Stream frame latency | Перед копированием кадра производителем → завершение предсказания | Копирование, очередь, ожидание процессора и обработка |
| Processing FPS | Число завершённых предсказаний / фактическое время окна | Включает накладные расходы измерительного цикла и ожидание кадров |

Время предсказания включает подготовку входа провайдером, модель, постобработку
и нормализацию результатов на CPU. Это не чистое время forward. CUDA синхронизируется
до и после вызова. Не измеряется максимальная асинхронная пропускная способность.
Изображения читаются заранее и циклически используются в заданном порядке.
Чтение файлов, декодирование, загрузка весов и графики исключены из окна.
Последний вызов может закончиться позже заданной длительности; FPS использует
фактическую длительность. Освобождение результатов и запись скалярных наблюдений
входят в общее время FPS, но не в latency отдельного вызова.

В потоке очередь содержит только последний непрочитанный кадр. `dropped` — число
замен таких кадров, а не число пропущенных временных слотов производителя.
`generation_fps` может отличаться от заданной частоты. Счётчики снимаются на
границах окна: первый обработанный кадр может быть создан до начала окна,
последний произведённый — остаться непрочитанным. Поэтому нельзя автоматически
интерпретировать `generated - processed` как число потерь. При очень низкой частоте
ожидание следующего кадра может существенно продлить окно.

Среднее, медиана, P95/P99 и ECDF используют все наблюдения. На графиках каждый
повтор представлен отдельно; вертикальные интервалы — наблюдаемый min/max,
не доверительные интервалы. Повторы не объединяются для расчёта перцентилей.
Обратная frame latency не является processing FPS.

Отдельная ячейка строит FPS во времени для каждой модели и устройства.
`FPS_BIN_SECONDS` задаёт ширину окна (по умолчанию 1 секунда): число завершений
в окне делится на его длительность. Последнее неполное окно использует фактическую
длительность; окна без завершений показывают 0 FPS. Это не обратная задержка кадра.
Режимы и входные частоты разнесены по панелям, повторы — по линиям.
Ещё одна ячейка показывает задержку в миллисекундах во времени для каждой модели
и устройства: по X — время завершения кадра относительно начала окна измерения,
по Y — измеренная задержка. Сплошная линия показывает `prediction_ms`, а для потока
пунктирная — `frame_latency_ms`, включая копирование и очередь. Все кадры и выбросы
сохраняются на графике, без усреднения по временным окнам.
Таблицы и графики по умолчанию читают последний выполненный режим; для другого
задайте `SAVED_RESULT_DIRECTORY = DIRECT_RESULT_DIRECTORY` или
`SAVED_RESULT_DIRECTORY = STREAM_RESULT_DIRECTORY` и повторите ячейки визуализации.

## Память: реализованные измерения

Все сырые значения сохраняются в байтах; таблица и графики переводят их в MiB
(2²⁰ байт). Размер checkpoint не является потреблением памяти.

| Показатель | Значение и ограничения |
| --- | --- |
| `rss_baseline_bytes` | RSS рабочего процесса после импорта PyTorch и чтения изображений, до загрузки модели |
| `rss_warm_bytes` | RSS после прогрева перед данным окном |
| `rss_sampled_peak_bytes` | Максимальный отсчёт RSS процесса в окне с шагом 10 мс и граничными отсчётами |
| `cuda_baseline` | Allocated/reserved до загрузки модели, в manifest рабочего процесса |
| `cuda_*_bytes_warm` | Allocated/reserved после прогрева |
| `cuda_*_bytes_peak` | Пики PyTorch CUDA allocator после сброса счётчиков непосредственно после прогрева |

RSS включает интерпретатор, библиотеки, изображения, модель и измерительные структуры,
но не память отдельного kernel и дочерних процессов SDK. Это память процесса, а не
изолированный размер модели. Разность с baseline также не является точным размером
модели. Потоковый sampler может пропустить короткий пик, особенно при удержании GIL;
10 мс — запрошенный интервал, фактические timestamps сохраняются. Граничные отсчёты
слегка охватывают запуск/остановку потока. Длинные запуски накапливают скалярные записи,
что тоже отражается в RSS. Пик загрузки и холодного старта не измеряется.

Allocated описывает занятую тензорами память, reserved — память под управлением
кэширующего аллокатора PyTorch. Это не полный объём VRAM процесса: контекст CUDA,
сторонние аллокаторы и другие процессы могут давать дополнительные расходы.
На CPU CUDA-поля равны `null`, а не нулю. RAM, allocated и reserved нельзя складывать.
Семантика RSS описана в [psutil](https://psutil.readthedocs.io/stable/#psutil.Process.memory_info),
а сброс пиков и reserved — в документации
[PyTorch reset_peak_memory_stats](https://docs.pytorch.org/docs/stable/generated/torch.cuda.memory.reset_peak_memory_stats.html)
и [max_memory_reserved](https://docs.pytorch.org/docs/stable/generated/torch.cuda.memory.max_memory_reserved.html).

## Другие возможности и расширения

- **CPU:** реализованы wall-clock latency и RSS. Для сравнения фиксируйте число
  потоков, частоты, питание и фоновую нагрузку. USS/PSS могут уточнить частную и
  совместную память, но зависят от ОС и дороже RSS; сейчас не собираются.
- **Дискретная NVIDIA CUDA:** реализованы синхронизация и статистика PyTorch.
  NVML / `nvidia-smi` можно добавить для памяти устройства или процесса,
  температуры, мощности и частот. Это отдельные выборочные показатели с собственной
  областью учёта; сейчас они не собираются.
- **Apple MPS:** текущий runner отклоняет это устройство. Расширение потребует
  `torch.mps.synchronize()` и выборочного сбора текущей памяти тензоров/драйвера,
  с проверкой доступности API в установленном PyTorch. CUDA peak API неприменим.
  Unified memory нельзя трактовать как независимые RAM + VRAM.
- **Jetson:** обычный путь CUDA может работать при совместимых PyTorch/SDK,
  но специализированная проверка Jetson не проведена. Для системной RAM,
  температуры, частот и режима питания нужны отдельные записи, например `tegrastats`
  и конфигурация `nvpmodel`. Общая память CPU/GPU требует единой области учёта;
  не суммируйте RSS и CUDA allocated. Реализация такого сборщика — отдельное расширение.
- **Чистый forward / CUDA events:** отдельный benchmark с заранее подготовленными
  тензорами; не сопоставляйте его напрямую с нынешним adapter latency.
- **Реальное видео / камера:** потребуются измерения захвата, декодирования и
  времён кадров. Синтетический поток этого не заменяет.
- **Полный конвейер:** детектор → защитные области → HSV → маска сорняков требует
  отдельного измерения. Этот ноутбук не реализует конвейер и не оценивает качество.

## Сохранение и воспроизводимость

Новый каталог `experiments/benchmarks/<UTC-time>-<id>/` содержит общий manifest,
отдельные каталоги пар модель/устройство, логи worker, JSON каждого завершённого
повтора и сводные JSON/CSV. Сохраняются SHA-256 весов и входов, размеры изображений,
версии пакетов, устройство, параметры предсказания, seed, потоки PyTorch и настройки
TF32. Укажите в `RUN_NOTES` режим питания, оборудование и внешние ограничения.
Для RF-DETR отсутствие `imgsz` означает разрешение, восстановленное из checkpoint;
hash весов фиксирует этот выбор. Значения по умолчанию SDK определяются сохранённой
версией провайдера. Это не автоматическая проверка фактической точности каждого слоя.

При ошибке worker общий manifest получает `failed`, лог содержит traceback.
При прерывании notebook дочерний процесс завершается; незаконченный повтор не
сохраняется, законченные доступны через `load_runs`. Worker manifest после
принудительного завершения может остаться `running`; статус всего запуска находится
в корневом manifest. Для графиков достаточно указать существующий каталог результатов.
Генерируемые результаты не следует добавлять в Git вместе с кодом.

Ни FPS, ни повторение фотографии не подтверждают качество реального видео,
качество масок или безопасность физических действий. Историческая выборка из
110 изображений не служит новым baseline. Автономные тесты с mock-провайдерами
проверяют программную логику, а не скорость или качество реальных моделей.
